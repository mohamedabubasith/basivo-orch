# basivo-orch — contributor rules

Monorepo: `apps/api` (FastAPI + SQLAlchemy, managed by `uv`) and `apps/web`
(React + Vite + Tailwind v4).

## Commands

```bash
make dev                                   # API + worker + web together
make worker                                # the run worker on its own
cd apps/api && uv run pytest -q            # backend suite (SQLite, no containers)
cd apps/api && uv run ruff format . && uv run ruff check .
cd apps/web && npx tsc -b --force          # the real typecheck — plain `tsc --noEmit`
                                           # checks NOTHING here (solution-style tsconfig)
cd apps/web && npx oxlint src && npm run build
```

## Adding a node type — the checklist is enforced, not advisory

Every new node ships with ALL of the following, in the same change. Two of
these are backed by tests that fail the suite if skipped:

1. **Register it**: class in `apps/api/basivo_orch/flows/nodes/`, added to
   `_NODES` in `nodes/__init__.py`. The palette, validation, and dispatch all
   read from that one tuple.
2. **Declare `output_paths`** — the dotted paths the editor's template
   autocomplete offers (`("body", "usage.cost_usd")` → `{{ input.body }}`).
   Empty tuple if the output shape is the author's own. Asserted in
   `tests/flows/test_output_paths.py`; the API response schema
   (`NodeTypeRead`) silently strips fields it does not name, so a schema
   update is part of any palette-field addition.
3. **Unit tests** for the node's own behaviour and config validation
   (`tests/flows/test_<node>.py`). Config that promises behaviour with
   nothing behind it must fail validation — see the webhook-secret and
   code-tool validators for the pattern.
4. **Engine integration coverage** in
   `tests/flows/test_engine_integration.py`: a real graph through the real
   `Engine.execute()`, and the type added to `EXERCISED_NODE_TYPES`.
   `test_every_registered_node_type_has_integration_coverage` fails the whole
   suite for any registered node missing from that set — registering a node
   without integration tests is a red build by construction.
5. **Live path, when the node talks to an external service**: extend or
   mirror `tests/flows/test_live_provider.py` — opt-in via environment
   variables, skipped otherwise, so real-API verification exists without CI
   ever holding a secret. Run it before shipping provider-touching changes:
   `BASIVO_LIVE_API_KEY=... uv run pytest tests/flows/test_live_provider.py`.
6. **Frontend**: an icon + accent in `apps/web/src/builder/nodeIcons.tsx`
   (palette and canvas share it). Config renders automatically from the JSON
   schema; special-case the inspector only when a field needs a bespoke
   control (see the agent's credential/model pickers, the code editor).

## Contracts that bite

- Templates address earlier results as `nodes.<id>.output.*` — the engine
  wraps outputs in `template_context()`. Do not expose raw values at
  `nodes.<id>.*`; that mismatch shipped once and every editor suggestion
  failed at run time until the integration suite caught it.
- User code (Code node, agent code tools) runs ONLY through
  `nodes/code.py::run_python` — one sandbox (isolated interpreter, CPU rlimit,
  wall timeout, empty environment), one place to harden. Never spawn a second
  variant.
- `apps/api/basivo_orch/auth/` is generated by basivo-auth; `copier recopy`
  overwrites it. Local edits are listed in `docs/generated-code-edits.md` and
  guarded by tests — re-apply after any recopy.
- Alembic: `basivo_orch/models.py` must import every model module, or
  autogenerate emits DROPs for the tables it cannot see.
- A new top-level route prefix (like `/hooks`) must ALSO be added to the
  `@api` path matcher in `apps/web/Caddyfile`, or production serves the SPA's
  index.html for it while dev (which routes by origin, not path) works fine.
- Nodes run CONCURRENTLY (engine waves). The run's single `AsyncSession` is
  not concurrency-safe, so every database touch goes through `Engine._db` —
  including `EventWriter`, which shares that lock. Node code that needs the
  database must go through the engine, never `ctx` to a session of its own.
- Agents run on **LangGraph** (`langchain.agents.create_agent`), not
  pydantic-ai. Models come from `nodes/models.py::build_chat_model` — one
  table, where 17 of 20 providers are `ChatOpenAI` with a different base URL.
  Tests use `tests/flows/fakes.py::FakeChatModel`, so the suite still needs no
  API key. LangChain reports tokens but never money: cost comes from
  `price_of` via genai-prices.
- The API does NOT execute runs. It writes them QUEUED and returns;
  `basivo_orch.worker` claims them (`FOR UPDATE SKIP LOCKED`) and executes
  them, and also owns the schedule ticker. If runs sit queued, no worker is
  running. The only inline path left is `mode=sync`, where the caller is
  explicitly holding the connection open.
- Files (posters, exports) are `Artifact` rows, saved through
  `ctx.save_artifact` and read through `ctx.load_artifact` — never passed as
  bytes through the graph, which would land in every run's stored summary.
  They live in Postgres because the API and worker are separate containers;
  `Engine.MAX_ARTIFACT_BYTES` is what keeps that honest.
- Video (`video.render`) shells out to HyperFrames (`hyperframes@0.8.3`,
  Apache 2.0) — Node 22+ and FFmpeg are required in the worker image, and
  `BASIVO_HYPERFRAMES_BIN` points at the binary. Unlike the poster node it
  MUST run JavaScript (the animation is JS), so a composition is code: the
  subprocess gets a stripped environment and a wall-clock cap.
- Every colour in a video template needs a `var(--x, fallback)`. A
  composition rendered with only some variables otherwise produces an invalid
  gradient and a black video — caught by looking at a frame, not by a test.
- Posters are RENDERED, not generated: a model writes HTML, `design.render`
  screenshots it in headless Chromium with real fonts. Image models get
  typography wrong about one time in ten and never say so. The worker image
  therefore needs `playwright install chromium`.
- A node that changes anything outside this system sets `replay_safe = False`.
  Recovery re-runs a graph from the START, so a run whose autofix already
  opened a PR must not be replayed — the reaper fails those for a human
  instead. `test_every_node_declares_whether_repeating_it_is_safe` pins the
  list.
- Agent memory is OUR table (`AgentMemory`), not LangGraph's checkpointer:
  `AsyncPostgresSaver` needs psycopg while this app is asyncpg throughout, and
  a checkpointer stores whole message lists including tool payloads. Only the
  human turn and the final reply are kept — tool calls are where credentials
  and third-party bodies live, and a memory table is the wrong place to
  accumulate those. Scope is `flow_id:node_id` (not the version, or every
  publish would wipe it) and the subject comes from the node's rendered
  `memory_key`; a key that renders empty is an ERROR, because falling back to
  a shared thread would let two counterparties read each other's history.
- Agent skills are progressive by design: the system prompt gets a CATALOGUE
  (name + description per skill), never the bodies. A body enters the
  conversation only through the `load_skill` tool result, and `SkillBudget`
  caps the total characters one run may admit. Pasting instructions into the
  prompt instead would make a library of thirty skills cost thirty procedures
  on every run — the whole point is that it costs thirty lines.
  `parse_skill_md` accepts Anthropic's SKILL.md, so a skill folder written for
  Claude imports unchanged; keep that format working.
- Narration is written and SPOKEN before the composition is authored. The
  reverse order cuts the voice off at every scene boundary, so the agent gets
  the measured audio length and the per-word timings and writes the animation
  to fit. `ensure_duration` is the backstop when it ignores them.
- The voice model must be the `-timestamped` Kokoro export, and
  `load_engine()` flips `has_timings` by hand because upstream looks for an
  output named `duration` while the export says `durations`. Get either wrong
  and the voice still works while captions silently become impossible.
- HyperFrames mixes audio itself: an `<audio src>` inside the stage is picked
  up by the render's ffmpeg graph (verified — `hasAudio: true`, an AAC stream
  at -22.8 dB). Never write a second muxing path. Caption timing must be
  appended to `window.__timelines[id]`, never CSS animation — the renderer
  produces frames by SEEKING that timeline, so a CSS animation renders as one
  frozen frame.
- The composition probe must multiply opacity down the ANCESTOR chain.
  `opacity` does not inherit as a computed value, so a heading inside an
  `opacity: 0` clip computes to 1 — reading only the element's own style
  passed a composition that rendered thirty seconds of black with a
  voice-over over it. It also samples every ~2s (`probe_moments`), because
  three points caught total failures and missed an eight-second dead tail.
- `strip_audio` runs before narration is injected. Told "a voice is already
  recorded", an agent added `<audio src="voice.mp3">`; there is no such file,
  and the renderer treats a missing media source as a correctness error and
  produces NOTHING. Self-closed tags are stripped first — otherwise a stray
  `<audio/>` pairs with a later `</audio>` and everything between them, real
  composition markup included, is deleted.
- The injected caption script waits for `window.__timelines[id]` (poll plus
  load/DOMContentLoaded). A composition may build its timeline on `load`, and
  a caption layer that gave up produced a video with a voice and no words.
- The deployment is capped at HALF the box (~7.9 GB of 16, worker CPU 1.8 of
  4). CPU-bound nodes declare `heavy = True` and the engine admits one per
  process (`heavy_slot()`); the list is pinned by
  `test_the_cpu_bound_nodes_are_the_ones_marked_heavy`. Two workers × two runs,
  not one worker × four: a worker recycled for memory should cost half the
  capacity, not all of it.
- Memory is bounded rather than trusted: the voice model is dropped after
  ten idle minutes, and the worker exits when its RSS passes
  BASIVO_WORKER_RSS_LIMIT_MB *while idle* so Docker restarts it. Never recycle
  with runs in flight — that trades a memory problem for abandoned runs.
  `resident_mb()` reads /proc, not `ru_maxrss`, which is a high-water mark and
  would make a worker restart forever after one expensive render.
- The worker has its OWN image target (`--target worker`): FFmpeg, Node 22,
  HyperFrames, Chromium and the voice model, ~700MB the API has no use for.
  HyperFrames renders with puppeteer-core, which bundles NO browser — left
  alone it downloads Chrome 152 on the first render in every fresh container —
  so `HYPERFRAMES_BROWSER_PATH` points at Playwright's Chromium. Not the
  chrome-headless-shell it prefers: that has no linux/arm64 build, so pointing
  at Playwright's is the only choice that works on both architectures.
- Two site addresses in the Caddyfile must be DISTINCT. Setting
  CONSOLE_ADDRESS == LANDING_ADDRESS is an "ambiguous site definition" error,
  not a no-op; the single-host deployment uses the inert
  `http://landing.localhost` default instead.
- `git.autofix` has two engines. With an Anthropic credential and Claude Code
  installed (`auto`), the repair is done by the Claude Code CLI in a headless
  subprocess over a tar.gz copy of the tree: file tools only (no Bash, no web),
  `--bare`, its own throwaway HOME, key in the environment and nowhere else,
  `--max-budget-usd` from `cost_limit_usd`. Every other provider gets the
  builtin tool loop, because Claude Code only runs Claude models. The protected
  path guard runs on the DIFF afterwards and fails the whole fix; a PR minus
  its CI change is not the fix the summary describes. Tests hide any real
  `claude` on PATH via an autouse fixture; set BASIVO_CLAUDE_CODE_BIN to a fake.
- Billing has ONE switch, `BILLING_MODE`. In `demo` nothing is enforced, the
  provider is never called and `/billing/webhook` is a 404; in `production` the
  free plan applies to everyone. Limits are enforced at the choke points
  (`create_run`, `create_flow`, `invite_member`, `list_runs`), never in routes,
  or the schedule ticker and the webhook path would run for free. The plan in
  force is computed from the subscription row plus the clock, never stored:
  a grace period that expires needs no job, and a job whose failure hands out
  a free upgrade is not a design. See `docs/billing.md`.
- The HTTP node STREAMS and stops at `MAX_RESPONSE_BYTES`. The limit used to
  run after `response.content`, so a 2GB reply was downloaded in full and held
  in memory before being rejected — a bandwidth bill and an OOM-killed worker
  in exchange for an error message. A declared over-limit `content-length` is
  refused before any body is read; an under-declaring server is caught by
  counting arriving bytes. Body text is decoded from the captured bytes, never
  `response.text` — a streamed body is closed and would raise.
- A render checks free disk first. Filling the volume does not fail a render,
  it stops Postgres accepting writes and takes the product down.
- Chromium in Docker needs `shm_size: 512m`. The default 64 MB /dev/shm makes
  a 1080p capture crash with an error that never mentions shared memory.
- Speech inference runs through `asyncio.to_thread`. On the event loop it
  blocks the worker's heartbeat, and a run whose heartbeat stops is one the
  reaper takes away mid-render.
- Any process that opens its own database session (the worker does) MUST
  `import basivo_orch.models`, or foreign keys to auth tables cannot resolve
  and every query dies at mapper configuration. The API only escapes this
  because its routers import the auth models anyway.

## Canvas connection rules

`apps/web/src/builder/connections.ts` refuses a connection while it is being dragged; `validate_graph` in `graph.py` refuses the same graph at save time. Every rule exists in both places and the server's wins. Rules: no self-connection, nothing into a trigger, one incoming connection per node, the source port must be one the node declares, handover only into `agent.llm`, no loops. Adding a rule means adding it to both files and to both test files (`connections.test.ts`, `test_graph.py`).

## Text a user reads

**No em-dashes, en-dashes or `--` in anything a customer sees.** Buttons,
labels, hints, placeholders, empty states, node names and descriptions, field
help, error messages, progress lines, landing copy, emails. The dash-aside
("confirmed — check again", "Off — every run starts fresh") is the single
clearest tell that a machine wrote the interface, and a product that reads as
machine-written is not trusted with a credential.

Use ordinary punctuation instead, chosen per sentence rather than substituted
blindly:

| Instead of | Write |
|---|---|
| `Off — every run starts fresh` | `Off (every run starts fresh)` |
| `Not valid JSON — the last value is saved` | `Not valid JSON. The last value is saved` |
| `Heart — warm US female` | `Heart (warm US female)` |
| `No API key — paste it into GitHub` | `No API key: paste it into GitHub` |
| `Pasted once — never shown again` | `Pasted once, never shown again` |
| `—` as an empty cell | `-` |

A comma is not always right: `Appears after you publish, an unpublished flow
has no stable id` is a comma splice. If both halves stand alone, use a full
stop.

`test_no_ai_dash_in_user_facing_text` enforces this over the frontend and the
API. Code comments and engineering docs are exempt — they are notes to
ourselves, and this repository's comments use em-dashes throughout.

## Verification bar

Backend claims are proven by pytest; UI claims are proven in a real browser
(playwright), not by "it compiles". When a run/flow behaviour is asserted,
read it back from the database or the `run_event` log rather than trusting
the response alone.
